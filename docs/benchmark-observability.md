# Нагрузочное тестирование и телеметрия Avito Recap

Предлагаемый путь в репозитории — `docs/benchmark-observability.md`. Статус — спецификация реализации. Приведённые ниже нагрузки задают условия эксперимента. Измеренные показатели появятся после запуска на описанном стенде.

## 1. Какие вопросы должен закрыть стенд

1. Сколько **новых** recap/с система может принимать и доводить до готового snapshot при устойчивой очереди?
2. Если пользователь ждёт дольше, где теряется время — при приёме HTTP, ожидании worker, чтении событий из ClickHouse, генерации или сохранении в PostgreSQL?
3. Что происходит с уже принятыми запросами при падении worker или зависимости? За сколько времени система догоняет входящий поток после восстановления?
4. Сколько стоит показать прогресс через SSE или polling при той же интенсивности генерации?

**Первый релиз (MVP)** покрывает вопросы 1 и 2, single-node VictoriaMetrics, Grafana, k6, сверку PostgreSQL и четыре сценария из раздела 5. Второй этап добавляет A/B путей доставки, отказы и SSE. Централизация логов — отдельный эксперимент после получения baseline.

## 2. Что учитывать в этом репозитории

| Участок | Поведение в текущем коде | Следствие для теста |
|---|---|---|
| `backend/cmd/bench-api/main.go` | Семафор удерживается от POST до завершения polling. При заполнении слотов отправитель ждёт, затем может догонять расписание пачкой. Таймаут или пустой ID увеличивают lost, время до failed попадает в выборку ready. | Старый smoke сохранить. Для capacity задавать независимый поток POST, проверять фактические старты. Для потерь нужна сверка принятого набора. |
| `scripts/benchmark-matrix.sh` | При 50 и 100 запросах/с подаются отдельные короткие серии с фиксированной скоростью. Burst из 1000 также ограничен concurrency. | Для ramp явно задать переходы и плато. Для drain сначала создать и подтвердить backlog заданной величины. |
| `internal/handler/recap_handler.go`, `internal/service/async_recap.go` внутри backend | Новый запрос и повтор для существующей незавершённой работы возвращают 202. Готовый snapshot возвращается сразу с 200. Сервер формирует ключ из профиля, года и версии алгоритма. | Регистрировать исход решения в сервисе. Смена HTTP-заголовка Idempotency-Key сама по себе не создаёт новый cold workload. |
| `backend/internal/repository/recap_request.go`, `backend/cmd/worker/main.go` | Создание запроса и запись команды в outbox идут в одной транзакции. В broker-режиме worker получает команду через Redpanda HTTP Proxy и захватывает конкретную работу в PG. В database-режиме worker сам ищет работу в PG. В hybrid активны оба пути. | Сравнивать способ доставки/захвата. В database-режиме остаются outbox и публикации событий. В hybrid фиксировать, какой путь выиграл claim. |
| `backend/internal/handler/recap_stream_handler.go` | Каждое открытое SSE-соединение перечитывает состояние с интервалом 250 мс по текущему Compose. Ответ закрывается на ready/failed. | 100 постоянно ожидающих клиентов создают до порядка 400 повторных чтений состояния в секунду плюс начальные чтения. Один вызов чтения может сделать несколько SQL-запросов. Замерять оба счётчика. |
| `docker-compose.yml`, `backend/cmd/bench-data`, `scripts/benchmark-*.sh` | Хостовые утилиты ожидают PG на localhost:5432, базовый Compose этот порт не публикует. В старых скриптах встречается сброс volumes. У части сервисов фиксированные container_name и host ports. | Запускать seeding и сверку из служебного контейнера в bench-сети. Для параллельного dev-стека изолировать имена, порты и volumes. Один новый Compose project name сам по себе коллизии не устраняет. |

## 3. Архитектура MVP

| Источник | Как собираем | Для чего |
|---|---|---|
| k6 | Генератор в bench-сети. Одна итерация capacity-сценария отправляет один POST. Итоговый файл локально, live-метрики по Prometheus remote write в VictoriaMetrics single-node на `/api/v1/write`. | Target/started POST/s, HTTP outcomes, latency и dropped_iterations. Снимок результата сохраняется при нарушении порогов. |
| Go API, outbox, каждый worker | Внутренний endpoint Prometheus в каждом процессе. VictoriaMetrics сама опрашивает endpoints раз в 5 с. Для реплик обеспечить обнаружение каждого адреса и проверить число живых targets. | Серверные histograms, результаты обработки, runtime. Запрос к /metrics читает собранные значения. |
| Состояние PG и брокера | Один sampler на стенд, доступный в bench-сети. Групповые запросы к PG каждые 5 с, финальная сверка отдельно. Из Redpanda собирать доступные метрики и offsets именно command topic/group. | Глубина, возраст очереди, outbox и lag. Сбой выборки виден как недоступность с возрастом последней успешной выборки. |
| Ресурсы | В MVP записывать CPU и память по контейнерам, включая k6 и VictoriaMetrics, с общими временными отметками. Можно переиспользовать Docker stats. Для PG дополнить Go sql.DB.Stats, для ClickHouse — длительностью чтения на стороне worker. | Отличить CPU/память генератора, ожидание соединения, запрос к БД и вычисления в worker. |
| Grafana | Provisioning источника VictoriaMetrics через Prometheus datasource и версионируемых dashboards. В отчёте хранить границы окна UTC. | Два экрана: «Вход и результат» и «Где образовалась очередь». |

Для первого релиза достаточно одного экземпляра VictoriaMetrics со scrape-конфигурацией. Закрепить проверенные версии образов. Настроить экспорт k6 Trend для выбранной версии и проверить имена рядов на smoke. Итоговый p95 брать из полного прогона k6 или из объединённых histogram buckets за измерительное окно. Усреднение p95 по репликам или интервалам даёт другой показатель.

## 4. Контракт измерений

| Величина | Определение |
|---|---|
| POST acceptance latency | На клиенте от начала POST до получения и проверки полного ответа. Основная выборка — валидный cold 202. Показать отдельно повторы 202, готовые 200, transport errors и ответы с ошибкой. Для HTTP-only времени использовать соответствующую метрику k6 с явным названием. |
| Скорости | На одной оси времени: запланированные итерации/с, начатые POST/с, вновь созданные работы/с, успешные финализации/с. Отдельно GET/s и повторные POST. Ready throughput считать по завершениям в интервале. |
| Server time to ready | Для успешных новых работ данного прогона разность finished_at и created_at в recap_requests. Это длительность по меткам БД. Очередь до первого claim — started_at минус created_at. Для повторных попыток отдельно измерять ожидание backoff и длительность попытки. |
| User time to ready | От начала POST до первого валидного snapshot у клиента через polling или SSE. Проверить ID, профиль, год и schema_version. Указывать способ наблюдения, число наблюдаемых работ и доли failed/timeout. Для polling соблюдать poll_after_ms. |
| Backlog и drain | Изолированная когорта cold-запросов. Backlog = queued + processing. Для опыта «1000 за 60 с» остановить все workers, принять и подтвердить ровно 1000 queued, закончить подачу, зафиксировать t0 при команде возврата workers. Конец — все 1000 готовы с валидными связями на snapshot. Отдельно показать время до первой готовности и опустошения outbox. Зафиксировать погрешность интервала наблюдения. |
| Потери и таймауты | Клиент пишет manifest попыток и полученных ID/ключей вне metric labels. После drain сверить с PG по ключам и ID. Разнести ready со snapshot, failed с причиной, queued/processing на deadline, подтверждённые 202 без записи, неоднозначные transport outcomes, отвергнутые POST и пропуски генератора. Timeout клиента может разрешиться в ready. |
| Дубли | Проверить один request на (profile_id, year, algorithm_version), один snapshot на (profile_id, year), связь ready → существующий snapshot нужного профиля и года. Для hot key много одинаковых ответных ID — ожидаемый результат. Повтор доставки и повтор snapshot считать отдельно. |

**Подача и наблюдение.** Capacity-поток не ждёт готовности. Практичный вариант manifest — потоковый локальный вывод событий запросов с объединением после теста по номеру итерации, без синхронной записи в PG на каждый POST. Проверить полноту manifest против k6 counters. Для пользовательского сценария использовать отдельную детерминированную когорту с polling или streaming-клиентом. Её доля и дополнительный RPS входят в описание нагрузки. При исчерпании профилей или пропуске итераций выводить «нагрузка не достигнута».

**Метрики для двух dashboards.**

- «Вход и результат» — четыре скорости из таблицы, p50/p95/p99 cold POST, server-ready и user-ready с числом наблюдений, доли snapshot hit/reuse, failed по стабильному коду, ошибки клиента, dropped iterations. Отмечать warm-up, измерение, fault, восстановление и drain.
- «Где образовалась очередь» — queued/processing, возраст старейшей ожидающей команды, outbox pending/publishing и возраст старейшей неопубликованной записи, publish latency/errors, consumer lag по партициям, claims по источнику, attempts/retry/expired lease, успешные и ошибочные DLQ-публикации. Для broker lag различать недоступную метрику и нулевой lag. В database-режиме lag не служит индикатором незавершённой генерации.
- На том же экране — длительность фаз «чтение activity из CH», «генерация», «финализация в PG», загрузка worker и PG pool wait. На втором этапе добавить время Mistral внутри генерации, исход provider/template fallback и число активных SSE-клиентов. Время вложенного provider входит в длительность генерации.
- HTTP labels ограничить шаблоном маршрута, методом, классом статуса. Аналогично нормализовать системный тег URL в k6 или отключить его, чтобы UUID из GET не создавали ряды. Для stage, outcome, source и error_code задать конечные перечни. ID профиля, запроса, команды, сырой URL и текст ошибки оставить в manifest/логах. Для сравнения запусков использовать временное окно и метаданные отчёта.

## 5. Сценарии и критерии

Значения нагрузки ниже — стартовые профили для калибровки. У холодной когорты каждая новая работа получает свою пару профиль/год. «Тёплый» означает наличие готового snapshot. Состояние системных кешей фиксируется отдельно.

| Этап и сценарий | Подача и данные | Что должно показать измерение |
|---|---|---|
| MVP · smoke | 100 новых профилей × 50 событий, 5 POST/с, затем drain. Небольшая фиксированная когорта проходит весь клиентский polling. | Сто созданных работ, сто связанных snapshots, ноль потерянных подтверждений и неожиданных failed. На Grafana видны API, outbox и все worker. |
| MVP · steady cold | 20 новых POST/с, 1 мин прогрев на отдельном наборе, 5 мин измерение, drain. На измерительное окно подготовить 6000 профилей, на прогрев ещё 1200. | Фактический вход соответствует плану, dropped=0. Для стенда проверить текущие ориентиры cold POST p95 ≤150 мс и <1% ошибок API. Показать ready/s, динамику возраста очереди и server-ready p95. |
| MVP · hot key + warm hit | На свежей паре при остановленных workers отправить 100 конкурентных POST. Возобновить workers, дождаться ready. Повторить 100 POST для той же пары. | Первая волна получает один ID в ответах 202, создаёт одну работу. Вторая получает snapshot с 200. Проверить неизменность числа работ и snapshots после второй волны. |
| MVP · backlog 1000 | Режим broker, три worker, все сначала остановлены. Ввести 1000 уникальных валидных работ, подтвердить backlog, вернуть три worker. | Критерий из bench/README — 1000 ready за ≤60 с на зафиксированном стенде. Отдельно показать результат correctness и производительности, включая превышение цели. |
| Этап 2 · capacity и A/B | Плавные переходы 20 → 50 → 100 cold POST/с за 30 с каждый, плато по 5 мин. Вблизи предела повторить ближайшую ступень дольше. Прогнать database, broker, затем hybrid на идентичном наборе. Для масштабирования отдельно сравнить 1 и 3 workers при фиксированном числе партиций (в Compose их 3). | Устойчивая ступень даёт нужный ingress без drops, соблюдает latency/error budget, завершения успевают за новыми работами, backlog и возраст не растут систематически. Отчёт приводит последнюю пройденную и первую нарушенную ступень, причину и длительность наблюдения. |
| Этап 2 · сбой и восстановление | По отдельности: kill одного worker во время processing, остановка Redpanda, остановка ClickHouse. Подавать 10 cold POST/с до, во время и после сбоя. Начальный опыт — 10 с недоступности. Сохранять фактические границы и остаток retry budget. | Проверить reclaim просроченной lease, рост outbox при outage брокера, классификацию CH retry/failed. Сверить все принятые работы после восстановления. Измерить время возврата к исходному backlog при продолжающемся трафике, затем финальный drain. |
| Этап 2 · SSE против polling | В двух опытах задать одинаковый вход и накапливать 100 ожидающих пользователей на разных работах. В первом подписываться на links.stream, во втором читать links.self с poll_after_ms. Затем отпустить накопленную работу. | Проверить первое событие и terminal ready/failed потоковым клиентом. Сравнить user-ready p95, активные соединения, вызовы чтения состояния/с, PG queries/s и CPU API. Сверить освобождение соединений при disconnect. Обычный буферизованный GET не измеряет время первого события. |
| Дополнительно · тяжёлые профили | Отдельные когорты по 50, 500 и 5000 activity events на профиль при одинаковом cold ingress. Выбрать rate ниже предела на первой когорте. | Сопоставить длительность CH-чтения и генерации, память worker и ready/s. Именно этот путь читает activity_events FINAL и декодирует JSONEachRow. |
| Дополнительно · медленный narrative | Базовый профиль — пустой MISTRAL_API_KEY, источник template. Затем локальный stub с фиксированными задержками и небольшой заданной долей таймаутов. | Сравнить занятость workers, очередь, fallback rate и time-to-ready. Успешная выдача template после ошибки провайдера видна отдельно. |

**Единые правила оценки.** Ошибка API — неожиданный HTTP outcome или transport error на попытку данного маршрута. Невалидное тело при ожидаемом статусе — отдельная ошибка контракта. Для steady вывести и общий error rate попыток POST, и каждую составляющую. Для happy-path correctness ожидаются ноль пропавших принятых работ и ноль лишних snapshots. Для fault заранее указать допустимые терминальные ошибки и предусмотренное контрактом восстановление. Явный failed учитывается в availability. Прогон с пропавшим manifest, обязательным источником данных или недостигнутой нагрузкой непригоден для вывода о capacity. Цель по user-ready p95 выбрать после baseline с привязкой к пользовательскому ожиданию.

## 6. Воспроизводимость и приёмка

1. Одна документированная команда из корня поднимает изолированный bench-стенд, ждёт health и готовности consumer, создаёт детерминированные данные и запускает smoke. Существующие `make bench-*` сохранить. Повторный запуск не трогает dev volumes. До теста сверить количество профилей и событий, достаточность активности, отсутствие старых snapshots и доступность измерителей.
2. Использовать текущие `bench-data`, `bench-environment`, при необходимости расширить `bench-report` и `bench-fault`. Один владелец seeding, один sampler. Разделить подготовку данных, warm-up, измерение, drain и сверку. После прогрева дождаться пустой очереди. При A/B восстанавливать одну исходную выборку, версию алгоритма, число workers/партиций, лимиты CPU/RAM и настройки retry/lease/poll.
3. Для оценки устойчивой пропускной способности выполнить минимум три сравнимых прогона на фиксированной машине, менять порядок A/B. Показать каждый результат, медиану по прогонам и разброс. P99 в маленьком smoke диагностический. Для измерения задавать запас VU по пиковому ingress и длительности итерации, контролировать drops и ресурсы генератора.
4. Результат в `bench/results/<run-id>/`: environment и git SHA, seed, workload и число событий, режим и фактическое число реплик, версии и лимиты, режим narrative, UTC-границы фаз, k6 summary, manifest, результат DB-сверки, fault timeline при наличии и короткая Markdown-сводка. Сохранять минимум целевые и фактические rates, выборки и знаменатели, latency, пропуски, backlog, drain, статус каждой цели. Исключить секреты из выгрузки окружения.
5. Smoke проверяет поступление рядов k6, свежие scrape всех ожидаемых targets и данные dashboards. Целевой сбой сверки или порога даёт ненулевой exit code с сохранённым отчётом. Быстрый функциональный smoke пригоден для CI. Абсолютные latency/drain gates включать на фиксированном runner. Нагрузочные и fault-сценарии доступны отдельным запуском.
6. Готовность MVP подтвердить реальным smoke, steady, hot/warm и backlog run. Падение проектной цели фиксировать вместе с данными. Вердикт о производительности и исправность самого измерителя указывать отдельно.

## 7. Опциональные логи

Для начала сохранять структурированные JSON-логи API, outbox и workers на время прогона. По одному recap_request_id должно быть возможно найти приём, publish, попытки worker и финализацию. Для брокерной доставки сохранять command_id, attempt и при наличии partition/offset. Не включать тело snapshot и prompt провайдера.

Если после fault-тестов понадобится интерактивный поиск, добавить отдельный Compose-профиль: OpenTelemetry Collector Contrib читает доступный источник логов, пакетно пишет в отдельную базу ClickHouse с TTL, Grafana читает её через ClickHouse datasource. Проверить схему exporter на установленном CH 24.8, доступность источника логов в Docker Desktop/Linux и поведение при остановленном CH. Ограничить очередь и память collector, считать dropped logs. Сравнить одинаковый прогон с доставкой логов и без неё: общие CPU, диск и merge в CH могут повлиять на чтение activity. Локальные логи нужны и во время отказа самого CH. Elasticsearch и Kibana имеет смысл добавить отдельным экспериментом, если целью станет именно изучение Elastic или его полнотекстового поиска.
