# Задание: «Итоги года»

## 1. Контекст

За год пользователь Авито совершает разные действия: просматривает объявления, добавляет их в избранное, общается с продавцами и покупателями, покупает и продаёт. В продукте пока нет готового перечня активностей для «Итогов года», поэтому команда должна сама определить состав данных и правила их интерпретации.

Задача — спроектировать MVP веб-приложения, которое превращает действия пользователя в персональные, связанные итоги: показывает значимые факты и объясняет выводы.

Итоги должны одновременно приносить пользу пользователю и бизнесу:

- пользователь узнаёт себя в итогах, видит ценность своей активности и доступные возможности;
- Авито получает повод вернуть пользователя в продукт, усилить эмоциональную связь и подтолкнуть к следующему действию.

## 2. Бизнес-цели MVP

### 2.1. Мотивировать создать и досмотреть итоги

Сценарий должен вызывать интерес, развлекать, удивлять и поддерживать эмоциональную связь пользователя с Авито.

### 2.2. Превратить активность в персональную историю

Пользователь выбирает профиль, запускает генерацию и получает понятный связный рассказ о своём годе, а не набор несвязанных показателей.

### 2.3. Показать ценность действий на площадке

Итоги должны отражать:

- основные интересы пользователя;
- наиболее частые и значимые действия;
- важные категории и сценарии;
- возможности, которыми пользователь ещё не воспользовался.

### 2.4. Вернуть пользователя в продукт

После просмотра итогов должен быть логичный следующий шаг: вернуться к интересующим объявлениям, продолжить начатый сценарий или совершить новое действие.

### 2.5. Обеспечить безопасность и уместность данных

Нельзя раскрывать чувствительную информацию, личные переписки, точные покупки и данные других пользователей. Нужно явно разделить сведения, допустимые в личных итогах, и сведения для публичной карточки.

## 3. Обязательный пользовательский сценарий

1. Пользователь открывает веб-приложение.
2. Выбирает один из доступных профилей.
3. Запускает генерацию «Итогов года».
4. Сервис анализирует активность выбранного профиля по воспроизводимым правилам.
5. Пользователь последовательно просматривает персональные карточки recap.
6. Интерфейс показывает, какие действия признаны важными, какие выводы и ачивки сформированы и почему.
7. В финале пользователь получает релевантное следующее действие внутри продукта.
8. При наличии функции публикации формируется отдельная безопасная публичная проекция.

Необходимо предусмотреть ключевые состояния: выбор профиля, запуск и ожидание генерации, успешный результат, недостаток данных и техническая ошибка.

## 4. Правила генерации

MVP работает с заранее подготовленными или сгенерированными данными нескольких пользователей. Команда самостоятельно определяет:

- учитываемые действия пользователя;
- значимые показатели и способы агрегации;
- типы поведения или архетипы;
- правила назначения ачивок и бейджей;
- правила выявления незавершённых сценариев и упущенных возможностей;
- правила формирования следующей рекомендации;
- способ объяснить, почему пользователь получил именно такой recap.

Правила должны быть детерминированными и воспроизводимыми: одинаковые исходные данные и версия алгоритма дают одинаковый результат.

## 5. Профили

Нужно подготовить несколько профилей, демонстрирующих разные сценарии использования. Набор должен показывать не только основной сценарий, но и различия в поведении, рекомендациях и карточках, а также потенциал перехода к реальным пользовательским данным.

Рекомендуемый минимум:

- активный покупатель/исследователь;
- продавец;
- пользователь с незавершённым сценарием;
- профиль с недостаточной активностью.

## 6. Документация продуктового решения

В README и проектной документации необходимо:

- описать пользовательский путь и обосновать продуктовую логику, а не только перечислить экраны;
- указать, какую пользу получает пользователь и какую бизнес-задачу решает Авито;
- объяснить выбор данных, метрик, архетипов, ачивок и рекомендаций;
- описать границы приватности личного recap и публичной карточки;
- показать возможное развитие решения;
- описать ограничения MVP и ключевые архитектурные решения;
- прозрачно указать этапы и способы использования ИИ.

Дополнительные функции допустимы, если усиливают бизнес-задачу и не заменяют основной сценарий.

## 7. Технические требования

### Фронтенд

- React 18+;
- TypeScript;
- допускаются внешние библиотеки, включая UI-библиотеки, менеджеры состояния, ESLint, Prettier, Vite/Webpack, React Query/Axios и аналоги.

### Бэкенд

- Go;
- база данных выбирается командой, выбор необходимо обосновать;
- приложение поднимается через Docker Compose;
- конфигурация линтера бэкенда должна быть описана; `.golangci.yaml` требуется в корне проекта согласно формулировке кейса.

### Репозиторий и запуск

- общий репозиторий для фронтенда и бэкенда;
- запуск приложения через `docker-compose`/`docker compose`;
- README, достаточный для запуска и проверки без устных пояснений.

## 8. Ожидаемые артефакты MVP

- работающий сквозной пользовательский сценарий;
- несколько профилей и наборы активности;
- воспроизводимые правила расчёта;
- фронтенд и бэкенд в одном репозитории;
- выбранная и обоснованная база данных;
- Docker Compose-конфигурация;
- публичный API-контракт и пример готового recap;
- модульные тесты ключевой бизнес-логики;
- ESLint/Prettier для фронтенда и golangci-lint для бэкенда;
- README с запуском, архитектурой, API, сценариями и ограничениями;
- описание использования ИИ;
- по возможности — развёрнутая версия, доступная по ссылке.

## 9. Критерии оценки жюри

Каждый пункт оценивается от 0 до 5 баллов:

1. Обязательная бизнес-логика: полный основной сценарий, ключевые состояния и соответствие бизнес-задаче.
2. Дополнительный функционал: усиливает цель и органично встроен в сценарий.
3. README: самостоятельный запуск и проверка, зависимости, сценарии, API, ограничения и ключевые решения.
4. Тесты: модульные тесты наиболее важных участков.
5. Линтеры: настроены на фронтенд и бэкенд, правила обоснованы.
6. Дизайн и архитектура: понятный интерфейс, логичное разделение ответственности.
7. Продуктовые решения: ясная связь решений с бизнес-целями.
8. Качество кода: читаемость, структура, единый стиль, отсутствие мёртвого кода и автоматические проверки.
9. Доступность в интернете: жюри может проверить основной сценарий по ссылке.

## 10. Критерии готовности

MVP считается готовым, если:

- пользователь проходит путь от выбора профиля до финальной рекомендации;
- для каждого профиля результат воспроизводим;
- recap является связной историей и содержит объяснимые выводы;
- ошибки и недостаток данных отображаются корректно;
- публичная карточка не содержит запрещённых или чувствительных данных;
- критичная бизнес-логика покрыта модульными тестами;
- линтеры и форматтеры запускаются автоматически;
- проект поднимается одной командой через Docker Compose;
- README позволяет независимому проверяющему запустить и оценить решение;
- обязательные требования отделены от дополнительных функций.
